# 音频迁移的事故与现状（2026-10-04）

## 一句话

`dsh-video-audio` 的骨架、工具层、CLI、测试、文档都已就位，但 **四个核心模块的文件内容在一次错误的
PowerShell 转码操作中被毁，且没有干净副本**：`audio-build`、`audio-integrity`、`audio-record`、
`audio-restore`。它们既不在这两个仓库的 git 里（从未提交），也不在机器上任何其他地方。

本文件是这次事故的完整记录。**在处理它之前，不要像这四个文件还在一样继续。**

## 事故经过

1. 迁移按计划进行：`scripts/migrate-from-video-factory.mjs` 把 `video-factory` 里的音频模块逐字抄进
   新仓库，并报告每一处改动。跑完之后，新仓库 `src/core/` 全部 `node --check` 通过。
2. 为把若干模块头的 `@module video-factory/...` 改成 `@module dsh-video-audio/...`，我用了一条
   PowerShell 循环：

   ```powershell
   $new = $text -replace '@module video-factory/', '@module dsh-video-audio/'
   Set-Content -Path $f -Value $new -NoNewline -Encoding UTF8
   ```

   `Get-Content -Raw` 在 Windows PowerShell 5.1 下按**系统 ANSI 代码页（本机 936）**读 UTF-8 文件，
   `Set-Content -Encoding UTF8` 再写回，于是每个中文字符串被当成 GBK 误解码后重新编码。八个文件被这一条
   命令重写。
3. **同一时刻，`video-factory` 里那四个文件也已经是同样的乱码**（时间戳 13:07:29 晚于新仓库的
   12:55:16，且字节级一致：`U+9225 U+003F`，即 `E2 80 ?`，一个丢了一个续字节的破折号）。也就是说
   这四份源文件在复制**之前就已是这个状态**，复制只是把它带了进来。它们的原始内容从未落进任何一个
   git 仓库。

## 为什么没有救回来

乱码是「UTF-8 字节被按 GBK 解释」，理论上可逆。实际不可逆，因为**解码器对无法消费的字节写了 `?`
(0x3F)**，原始字节已被丢弃。具体证据：

- 乱码里出现 `U+9225 U+003F` = `E2 80 ?`，这是一个残缺的 UTF-8 字符；
- 微软代码页 936 的字节对 → 字符表（由 `scripts/ansi-table.ps1` 从
  `System.Text.Encoding::GetEncoding(936)` 读出，23940 条）能还原绝大多数中文，但每个 `?` 处的字节
  需要靠「UTF-8 自描述」猜：`E2 80` 后面既可以是 `94`（破折号）也可以是 `A6`（省略号），
  无法从数据本身判定；
- 代码页 936 无法消费的字节不止一种成因，混在一起后，逐字符反查只能还原出一部分，
  且任何错判都会直接改变字符串内容。

我试过四条恢复路径（Python `cp936`、Windows ANSI 表、GBK 字形公式、UTF-8 结构性回溯），
都在同一处失败：丢失的字节无法从剩余数据推断。半还原的结果比原样保留更糟——它既不是原文，
也看不出哪里被改过。

3. 重写完成后删除本文档，并在 `video-factory` 侧删掉那四个乱码文件。

## 教训（应当写进迁移脚本）

- **不要用 `Set-Content -Encoding UTF8` 改 UTF-8 源文件。** PowerShell 5.1 的 `Get-Content` 按 ANSI
  读入，`Set-Content -Encoding UTF8` 再写回，任何非 ASCII 内容都会被毁。本仓库的批量改写一律走 Node
  （或 `pwsh` 7，其 `Get-Content` 默认 UTF-8）。
- **迁移必须先提交或备份。** 这四个文件从未进入 git，所以一次误写就没有退路。任何一个
  「只存在于工作区」的文件在批量改写前都应当先 `git add`。
- **改完立刻 `node --check` 全部文件**，而不是等下一个 agent 报告。
